## 分支模型

- 功能与修复从 `dev` 出发；GitLab 为公司主仓（权威推送目标），GitHub 为镜像/CI 源
- `main` / `master` 为生产分支；发布以快进同步方式推进，不重写历史

## 标准流程

1. **准备**：确认分支与工作树状态（`git status --short --branch`），一次任务一个工作树
2. **开发与验证**：本地构建（`pnpm --filter <pkg> build`）与测试（`pnpm --filter api test`）
3. **运行时验证**：按需部署到调试环境，以部署状态、日志、健康检查三重证据确认
4. **评审**：对最终验证过的树做代码评审；发现问题回到第 2 步
5. **提交**：在 `dev` 上提交，记录提交 SHA，确认与验证过的树一致
6. **发布**：快进同步到生产分支，推送远端

## 交付红线

- 不在未验证的情况下标记完成；区分编译证据与运行时证据
- 不提交密钥、生成产物与无关改动
- 迁移、配置变更、真实发布等副作用均需单独授权
- 环境变量变更、部署、推送是三个独立阶段，互不隐含授权
